# Local Player Session Authority

## Goal

Phase 5 Group 2 gives every approved network connection exactly one server-owned player session and one client-owned network player actor. This closes the identity gap between the Group 1 handshake and later authoritative movement/gameplay replication.

The server is the only process allowed to create or end sessions, select actor identity, and spawn player objects. A client can request a validated `playerId`; it cannot provide its actor ID, session ID, network ownership, or session lifecycle state.

## Identity mapping

The connection and character identity layers remain distinct:

| Layer | Example | Owner |
| --- | --- | --- |
| Client instance | `f85...` | Generated by the client process and validated by the server |
| Player | `local-player` | Requested during connection; unique among active sessions |
| Session | `session.1.4` | Generated by the server for one connection lifetime |
| Actor | `actor.player.local-player` | Generated canonically by the server and stable across reconnects |
| Network client | `1` | Assigned by Netcode for the active transport connection |

`PlayerSessionRegistry` owns active mappings and rejects duplicate client or player ownership. Disconnecting removes the active session, while reconnecting the same player creates a new session ID and retains the same canonical actor ID.

## Runtime flow

1. The client sends the Group 1 versioned connection payload.
2. The server validates protocol, capacity, and active player uniqueness.
3. After transport connection succeeds, the server opens a `PlayerSessionSnapshot`.
4. The server instantiates the registered `NetworkPlayerActor` prefab.
5. The server writes session, client-instance, player, actor, and revision identity before spawn.
6. The server calls `SpawnAsPlayerObject`, assigning ownership to the approved client.
7. The client resolves `NetworkManager.LocalClient.PlayerObject` and exposes it through `LocalGameClient.LocalPlayerActor`.
8. On disconnect, Netcode despawns the player object and the server closes the session.

The actor prefab is intentionally presentation-free and has no movement or gameplay components. It is an authoritative identity anchor, not a duplicate of the current local prototype player. Group 3 can attach server-validated movement input and transform replication to this actor without moving the full coupled prototype stack at once.

Use `Tools > Unity Isekai Game > Networking > Bake Local Network Foundation` after changing the network prefab or scene host. The bake is idempotent: it normalizes the prefab, replaces stale registry entries, wires the server reference, and saves the Prototype Scene.

## Group 2 acceptance criteria

- One active session per connected client.
- One active session per case-insensitive player ID.
- Server-generated session and actor IDs.
- Stable actor ID and fresh session ID after reconnect.
- One spawned NGO player object owned by the connected client.
- Replicated identity available from the client's local player object.
- Session and actor cleanup after disconnect.
- No client authority over mutable world or character state.
- Separate-process server/client verification and full regression suites remain green.

## VS Code generated-project recovery

Unity owns the `.sln`, `.csproj`, and `Temp/obj` files. They are generated local state and are intentionally ignored by Git. Errors about missing `Temp/obj` caches or a newly added assembly project normally mean VS Code loaded the solution while Unity was refreshing or deleting that disposable state.

After an assembly definition changes:

1. Let Unity finish compiling.
2. In Unity, open `Edit > Preferences > External Tools` and select `Regenerate project files`, or run the installed Visual Studio Editor package's solution-generation command.
3. In VS Code, run `Developer: Reload Window`.

Do not commit `.csproj`, `.sln`, or `Temp` output and do not hand-edit their imports. The authoritative dependency graph is the `.asmdef` files under `Assets/_Project`.
